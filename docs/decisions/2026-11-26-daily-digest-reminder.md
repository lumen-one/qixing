# 决定：每日收尾提醒走站点表，只排下一次

记录：2026-11-26
状态：生效中

## 问题

今天的清单常常到晚上才发现还剩几件没动。任务自己的提醒只为"有具体时刻的那一件"响，
它们不回答"今天整体还剩多少"：散着改期、晚一点再看，成本很低，代价是当天过去了才发现。

直觉做法是挂一个每天 18:00 的重复闹钟，到点问一句"今天做完没有"。可这条提醒必须满足
两个条件：没有未完成的任务时不要响；响的时候说得出是哪几件。原生 `AlarmManager` 的
重复闹钟到点只有一句固定文案——应用被杀时没有 Dart 可以问"现在还剩什么"。

## 决定

- 每日收尾提醒是 `ReminderDispatcher` 的**第四个站点源**，站点 id `daily|<yyyy-MM-dd>`
  （仿编排的 `plan|` 前缀：它不对应任何任务，查不到是正常的）。
- **只挂下一次**：今天还没到设定时刻就今天，过了就明天。不预排未来几天——应用不在时任务
  本来也改不了，多挂几站只会在弃用后连着弹几天旧数字；每次重锚都会补下一站。
- 统计口径 = **今日页的编号条目**（逾期 + 开始型 + 截止型 + 插队件），与页面上的编号一一
  对应。挂起（长期意图）与页底散件（没有日期）不算，例行实例也不算——例行默认不响是用户
  自己的选择，绕过去等于把那条选择作废。一件都没有就当天不挂站。
- 正文报件数与前三个标题，标题是「今天还剩 N 件」。渠道恒 `ring`：不升级全屏闹钟，
  **不吃**通知时间段——它是用户自己定的钟点，不是"顺延送达"的软提醒。
- **过点不补**：设定时刻已过就顺延到明天。与时点提醒的 30 分钟补响宽限不同——那时用户
  多半正看着清单，这条提醒没有新信息。
- 与别的站撞在同一分钟时往后挪一分钟。默认的 18:00 恰好也是新建截止时刻的缺省值，撞车不是
  小概率；别的源落选还有"重锚挂到 `now+1s`"兜底，收尾这一站过点就顺延到明天——丢一次就是
  整天没有。
- 到点走带站点身份的路径，但没有 `point_fired` 可记（同编排站）：`delivered` 为假时照草案
  补投，随后重锚算出明天那一站。点通知打开今日清单。
- 设置落 `settings.json` 的 `daily_reminder_enabled`（缺键 = 开）与 `daily_reminder_minutes`
  （缺键 = 1080 = 18:00）。

## 备选与为什么输

- **原生 `setRepeating` 每天重复**：文案固定，说不出"还剩哪几件"，任务全做完也照响。要让
  它有条件，就得在原生里读任务文件、跑一遍今日视图——那是把 Dart 的一半搬到 Kotlin。
- **预排未来 7 天（与时点提醒同寿命）**：草案里的件数在挂站那一刻就冻住了。应用一周不打开，
  后几天弹的是第一天的数字；而应用真的活着时任何命令都会重锚刷新，所以只有"死了很久"这一种
  情况会用到那些站——恰好是旧数字最难看的时候。
- **每天只说"今天做完了吗"、不带件数**：信息量太低，连"要不要现在动手"都判断不了。
- **把挂起与散件也算进去**：挂起是长期意图（没有截止），散件没有日期，两者都会让它天天响，
  最后被人划掉关掉。
- **允许选星期（只在工作日响）**：多一个开关，先把"每天一次"用起来；真需要时再加。

## 代价

- 应用不在时它按挂站那一刻的件数说话（站点表是快照，见 [architecture.md](../architecture.md) §11）：
  件数在 18:00 前被改过、而应用一直没打开，数字会偏一次。
- 只挂下一次，意味着关机错过那一刻就没有这一天了，不补。
- 桌面壳的 `TimerAlarmPort` 只取最早一站，它要与时点提醒争表头；桌面关掉应用就什么都没有
  （与其它提醒一致）。
